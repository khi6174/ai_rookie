# SafeRoute AI 제품 명세

## 문서 상태

- 상태: Approved
- 담당: 팀 안전빵
- 최종 갱신: 2026-08-01
- 목표 릴리스: AI ROOKIE 본선 MVP, 2026-08-14
- 상위 가드레일: `AGENTS.md`

## 1. 제품 한 문장 정의

SafeRoute AI는 남은 라스트마일 배송계획에서 기사별 안전 임계치가 언제, 어디서 초과될지 예측하고, 실행 가능한 개입안을 비교하여, 위험을 다른 기사에게 전가하지 않는 방안을 기사 동의와 관리자 승인 아래 실제 배송계획에 반영하는 안전운영 코파일럿이다.

## 2. 문제 정의

기존 배송운영 시스템은 주로 거리, ETA, 비용, 적재량, 업무량 균형을 최적화한다. 운전자 안전 시스템은 졸음, 시선이탈, 급가속 같은 현재 또는 과거의 위험 신호를 감지하는 데 강하다. 그러나 안전 신호와 남은 배송계획을 함께 시뮬레이션하여 다음 질문에 답하고 실제 운영계획까지 바꾸는 공개 통합 제품은 확인하기 어렵다.

> 아직 임계치를 넘지 않았더라도, 현재 계획을 유지하면 언제 어느 배송지에서 안전한계를 넘으며, 어떤 개입이 모든 기사에게 안전하고 실행 가능한가?

SafeRoute의 차별점은 새로운 센서 하나나 정적인 점수가 아니라, 예측·설명·비교·합의·실행·감사를 하나의 폐루프로 연결하는 운영 의사결정 구조다.

### 2.1 제품 레퍼런스와 SafeRoute의 고유 위치

외부 제품은 기능을 합치거나 화면을 복제하기 위한 명세가 아니라, 이미 검증된 현장 문제와 상호작용을 이해하기 위한 경계가 있는 레퍼런스다.

| 계층 | 참고 제품·자료 | 가져올 특성 | SafeRoute가 새로 소유하는 것 | 가져오지 않을 것 |
|---|---|---|---|---|
| 기사 운행 경험 | [아틀란 트럭](https://play.google.com/store/apps/details?hl=ko&id=kr.mappers.atlantruck) | 지도 중심 운행 맥락, 현재·다음 지점, 배송 진행, 경로·순서 변화의 빠른 인지 | 안전 제약을 통과한 계획만 기사 동의·관리자 승인 뒤 경로·순서·ETA에 적용 | 자체 턴바이턴 내비게이션, 오더 중개·운임·수익 최적화, 운전점수 기반 평가 |
| 예방적 안전 신호 | [KBS 모빌리티 AI 영상](https://www.youtube.com/watch?v=NsgIRYv0c6I&t=243s)과 Riderlog 계열 공개 사례 | 사고 이후가 아닌 예방적 데이터 활용, 운전행동·안전 이벤트의 설명과 맞춤 피드백 | 업무량·날씨·지역·경로와 선택형 안전 신호를 남은 계획에 결합해 Time-to-Breach와 개입안을 계산 | 자동 사고 확정·구조 요청, 상시 행동감시, 센서 점수 기반 징계·보험·보상 |
| 운영 의사결정 | SafeRoute AI | 두 레퍼런스의 현장 맥락을 입력·표현 경계로 활용 | 미래 임계치 예측, 반사실적 개입, Risk Transfer Guard, Two-Key Control, 원자적 계획 적용과 감사 | AI의 자동 결정·집행, 안전과 ETA·비용의 가중합 교환 |

따라서 제품 포지셔닝은 `아틀란 트럭 같은 범용 내비게이션`이나 `영상 사례 같은 사고감지 시스템`이 아니다. SafeRoute는 이들 시스템이 제공할 수 있는 운행 맥락과 검증된 안전 신호 위에서 **누구에게 어떤 지원을 언제 적용할지 합의하고 계획을 바꾸는 안전운영 의사결정 계층**이다.

## 3. 제품 목표

### 3.1 궁극적 목표

SafeRoute AI의 궁극적 목표는 라스트마일 운영에서 안전을 사후 경고나 기사 개인의 점수가 아니라 **계획을 실행하기 전에 검증되는 운영 하드 제약**으로 만드는 것이다.

제품이 도달해야 할 최종 상태는 다음과 같다.

> 배송계획이 바뀔 때마다 모든 영향 기사의 미래 안전 가능영역을 검증하고, 위험 원인과 실행 가능한 대안을 같은 근거로 설명하며, 기사 통제권과 관리자 책임 아래 계획을 갱신하고, 그 결정이 실제 현장에서 감사 가능한 표준 절차가 된다.

궁극적 성공은 화면 수나 모델 규모가 아니라 다음 네 결과로 판단한다.

1. **예방 가능성**: 임계치 초과 전에 개입 가능한 시간과 위치를 안정적으로 제공한다.
2. **안전 형평성**: 한 기사의 위험을 다른 기사에게 전가하는 계획을 실행 전에 차단한다.
3. **인간 통제와 신뢰**: 기사와 관리자가 같은 근거를 이해하고 동의·수정·거절·승인을 추적할 수 있다.
4. **운영 적용성**: 승인된 결정이 경로·배송순서·작업량·ETA에 원자적으로 반영되고 실패 시 복구된다.

이 목표는 사고확률 예측, 의료 진단, 기사 성과평가 또는 자동 통제를 포함하지 않는다.

### 3.2 목표 달성 단계

| 단계 | 목표 | 종료조건 |
|---|---|---|
| 1. 결정론적 기반 | 계약·fixtures·Safety Budget을 재현 가능하게 구현 | 계약 테스트, 단조성, 세 대표 fixture 정확값 통과 |
| 2. 안전한 개입 | 하드 제약과 Risk Transfer Guard 구현 | 12건 이관 차단, 8건 조건부 가능, 동점 재현 |
| 3. 인간 중심 폐루프 | 기사 동의와 관리자 승인을 실제 상태기계로 연결 | 동일 결정 ID E2E와 원자적 계획 적용 통과 |
| 4. 국내 AI 근거 계층 | 문서·설명을 안전 결정과 분리해 고도화 | 숫자 불변, 인용, malformed·timeout fallback 통과 |
| 5. 본선 증명 | 3분 시연과 평가 산출물로 여섯 기준 입증 | clean start 3회, 30개 변형, 접근성·비교 결과 |
| 6. 파일럿 준비 | 실제 운영 입력과 권한·보존·동의 정책 검증 | 현장 승인 데이터 계약과 파일럿 안전·개인정보 검토 |
| 7. 공간운영 확장 | 다지역·다기사 의사결정을 지도와 현장형 PWA로 연결 | 합성 다지역 2D 폐루프, PWA·부하·접근성 Gate, 조건부 3D 검증 |

### 3.3 North Star와 가드레일 지표

North Star는 `안전 제약을 위반하지 않고 사람의 동의·승인을 거쳐 완결된 계획 조정 비율`이다. MVP에서는 실제 운영 성과가 아니라 결정론적 시뮬레이션의 폐루프 완결률로 측정한다.

함께 확인할 가드레일은 다음과 같다.

- 불안전 후보 추천·적용 건수: `0`
- 필요한 기사 동의 없이 적용된 건수: `0`
- LLM이 도메인 수치·추천을 변경한 건수: `0`
- 실패·Mock·Fallback을 Live 성공으로 표시한 건수: `0`
- 기사 순위·비난·거절 불이익 표현: `0`
- 적용 후 다른 기사의 임계치 초과 도입 건수: `0`

### 3.4 본선 MVP 목표

- 남은 배송지별 Safety Budget 변화를 결정론적으로 시뮬레이션한다.
- 첫 예상 임계치 초과의 시간과 배송지를 보여준다.
- 위험의 주요 기여요인, 신뢰도, 결측 입력을 설명한다.
- 휴식, 물량이관, 순서변경, 안전경로, Safe Delay를 비교한다.
- 수신 기사를 위험하게 만드는 물량이관을 차단한다.
- 기사가 같은 근거를 보고 동의, 수정 요청 또는 거절할 수 있게 한다.
- 관리자 승인 후 경로, 배송순서, 물량, ETA와 고객안내를 갱신한다.
- 조정 전후 결과와 의사결정 근거를 감사기록으로 남긴다.
- Live API 장애에서도 명시적인 Demo fixture로 3분 시연을 완주한다.

### 3.5 성공을 입증하는 대표 장면

관악구 우천·경사·장시간 작업 시나리오에서 현재 계획이 52분 후 17번째 남은 배송지에서 임계치를 초과할 것으로 표시된다. 시스템은 여러 대안을 비교하고, 12건 이관은 수신 기사를 위험하게 하므로 차단하며, `10분 휴식 + 8건 이관`은 양쪽 기사의 제약을 통과하는 추천안으로 제시한다. 기사가 동의하고 관리자가 승인하면 배송계획과 고객 ETA가 갱신되고 전후 지표와 근거가 기록된다.

이 장면의 수치는 데모 fixture의 초기 목표값이며, `docs/safety-model.md`와 결정론적 테스트에서 재현되기 전에는 확정 수치로 간주하지 않는다.

### 3.6 최종 제품 공간운영 목표

본선 MVP 이후 최종 제품은 전국·권역에서 지역·허브와 기사별 지원 decision으로 좁혀 가는 다지역 Control Tower와 설치 가능한 기사 PWA를 목표로 한다. 이 확장은 Safety Budget·Risk Transfer Guard·동의·승인 규칙을 바꾸지 않고 같은 결정 스냅샷을 공간적으로 탐색하는 표현 계층이다.

첫 구현은 실제 기사 위치가 아니라 최소 3개 지역·24명 이상의 결정론적 합성 fixture와 공급자 독립 2D 지도다. 실시간 위치, 실제 인증, 오프라인 명령과 2.5D·3D는 각각 개인정보·architecture·평가 Gate를 통과한 뒤에만 추가한다.

### 3.7 2026-08-14 합성 운영 서비스 목표

2026-08-14의 최종 완료 기준은 `docs/service-goal-2026-08-14.md`의 `PAID_PILOT_READY_WITH_SYNTHETIC_OPERATIONS`다. 기존 고정 Demo를 보존하되 다음 서비스 능력을 추가한다.

- 표준 합성 근무표·배송 작업표·경로표·안전검토표 원문의 파일 해시와 상위 레코드 참조를 검증하고 strict 추출 레코드로 정규화해 버전이 있는 일일 운영 스냅샷을 만든다.
- 스냅샷의 모든 활성 기사를 같은 평가시각에서 계산한다.
- 입력에서 파생된 복수 지원 decision을 생성하고 선택·처리한다.
- 다른 열린 decision과 최신 계획 버전을 포함해 Risk Transfer Guard를 다시 검사한다.
- 승인된 변경을 계획·배송순서·ETA에 원자적으로 반영하고 고객안내 초안·감사·내보내기를 만든다.
- 외부 AI·지도 실패에서도 결정론적 계산과 인간 승인 폐루프를 유지한다.
- Upstage 설명 Live와 Document Parse·Extract Live는 별도 Gate로 검증하며 어느 한쪽의 성공으로 다른 계층을 완료 처리하지 않는다.

서비스 완료는 실제 개인정보·GPS·비공개 TMS 쓰기·실제 고객 발송 또는 사고감소 효과를 포함하지 않는다.

#### 역할 분리

- 관리자는 기사 대신 동의·수정 요청·거절을 기록하지 않는다.
- 각 영향 기사는 동일한 `workspaceId`, `decisionId`, `courierId`로 열린 별도 Field-first 화면에서 직접 응답한다.
- 관리자는 저장소에서 최신 기사 응답을 다시 불러온 뒤에만 승인 단계로 진행한다.
- 실제 인증은 비목표이며 합성 운영 링크만 사용한다. 실제 사용자 인증·권한은 별도 재승인 대상이다.

## 4. 핵심 사용자

### 4.1 허브 관리자

#### 목표

- 향후 60분 안에 지원이 필요한 상황을 빠르게 찾는다.
- 가능한 개입의 안전효과, 지연, 실행복잡도와 형평성을 비교한다.
- 기사 응답과 수신 기사 영향을 확인한 뒤 조치를 승인한다.
- 계획 변경과 고객 영향을 추적하고 감사 근거를 남긴다.

#### 필요한 정보

- 예측 초과까지 남은 시간과 예상 배송지
- 주요 기여요인, 신뢰도, 결측값
- 개입별 조정 전후 결과
- 불가능한 후보와 불가능한 이유
- 기사 동의·수정 요청·거절 상태
- 수신 기사 이관 후 Safety Budget
- 변경된 경로, 배송순서, ETA와 고객안내

#### 보호 원칙

- 기사 순위, 저성과 분류, 경쟁 배지를 제공하지 않는다.
- 의사결정에 불필요한 원시 생체정보와 정밀 이동궤적을 보여주지 않는다.
- 지원 필요 상황을 기사 개인의 잘못처럼 표현하지 않는다.

### 4.2 배송기사

#### 목표

- 현재 계획을 언제까지 안전하게 수행할 수 있는지 이해한다.
- 위험 원인과 추천 조치의 효과·지연을 짧고 명확하게 확인한다.
- 조치에 동의하거나 수정·거절하고 그 이유를 전달한다.
- 정차 상태에서 근접사고를 간단히 신고한다.
- 어떤 데이터가 사용되며 관리자에게 무엇이 보이는지 확인한다.

#### 필요한 정보

- Safety Budget 범위와 위험 밴드
- Safe-until 시각과 예상 초과 배송지
- 기사 탓이 아닌 구조적 표현의 원인 3개
- 추천 조치 하나와 예상 안전효과·지연
- 물량이관 시 상대 기사도 안전 제약을 통과했다는 설명
- 동의, 수정 요청, 거절의 다음 단계

#### 보호 원칙

- 거절하거나 수정 요청해도 경고색, 위협 문구, 불이익 암시를 사용하지 않는다.
- 다른 기사와 비교하거나 순위를 매기지 않는다.
- 운전 중 긴 읽기나 텍스트 입력을 요구하지 않는다.

### 4.3 고객안내 수신자

#### 목표

- 안전운영으로 변경된 도착 예정시간을 이해한다.
- 기사 개인에게 책임을 돌리지 않는 간결한 안내를 받는다.

#### 필요한 정보

- 변경된 도착 예정시간
- 안전한 배송운영에 따른 변경이라는 짧은 설명
- 필요한 경우 문의 또는 변경된 배송상태 확인 경로

별도 고객 앱은 만들지 않는다. MVP에서는 문자·알림톡을 모사한 고객안내 화면 또는 메시지 결과로 충분하다.

## 5. 핵심 개념

### 5.1 Dynamic Safety Envelope

기사 상태, 작업 부하, 경로·지역, 날씨와 휴식에 따라 시간 및 배송순서별로 달라지는 안전 가능영역이다. 내부 엔진과 기술 문서에서는 `Dynamic Safety Envelope` 또는 `DSE`를 사용한다.

### 5.2 Safety Budget

DSE를 사용자에게 보여주는 운영상 안전여유다. 0~100 범위의 결정론적 지표로 시작하지만 사고확률, 건강진단, 기사 평가점수가 아니다. 단일 숫자만 제시하지 않고 범위 또는 위험 밴드, 변화 타임라인, 신뢰도와 함께 표시한다.

구체적인 공식, 임계치, 밴드와 가중치는 `docs/safety-model.md`에서 정의한다.

### 5.3 Time-to-Breach

현재 계획을 유지할 때 Safety Budget이 처음으로 임계치를 넘을 것으로 예상되는 시점까지 남은 시간이다. 함께 반환해야 하는 정보는 예상 시각, 배송지 순번, 배송지 또는 구간 ID와 해당 시점의 Budget이다.

예측 구간 안에 초과가 없으면 `no breach in forecast horizon` 상태를 명시한다. 값을 `0`, 빈 문자열 또는 임의의 큰 수로 대체하지 않는다.

### 5.4 운영 위험지수와 위험 밴드

운영 위험지수는 현재·미래의 작업 지속 가능성을 비교하기 위한 파생 지표다. 사고 발생확률로 해석하지 않는다. 위험 밴드는 최소 `안정`, `주의`, `지원 필요`, `임계치 초과`를 구분하되 정확한 경계는 안전모델 문서에서 확정한다.

상태는 색뿐 아니라 텍스트, 아이콘과 수치 범위로 표현한다. 빨강은 실제 임계치 초과에만 사용한다.

### 5.5 신뢰도와 결측 데이터

모든 예측에는 `HIGH`, `MEDIUM`, `LOW` 중 하나의 신뢰도와 누락된 입력 목록을 제공한다. 결측 입력이 늘어나면 신뢰도가 높아져서는 안 된다. 결측을 평균값으로 조용히 채우지 않으며, 대체값을 사용했다면 출처와 방법을 표시한다.

신뢰도는 사고확률의 신뢰구간이 아니라 현재 입력의 완전성, 최신성, 출처 품질을 나타낸다.

### 5.6 개입안

SafeRoute는 다음 다섯 종류와 호환 가능한 묶음을 비교한다.

1. 휴식: 일정 시간 휴식 후 회복을 반영한다.
2. 물량이관: 일부 배송지를 다른 기사에게 이전한다.
3. 배송순서 변경: 위험구간의 노출 시점이나 작업순서를 바꾼다.
4. 안전경로: ETA가 늘어도 위험노출이 낮은 경로를 선택한다.
5. Safe Delay: 저우선순위 배송을 지연하고 고객안내를 생성한다.

각 후보에는 안전효과, ETA 변화, 운영복잡도, 고객영향, 수신 기사 형평성, 실행 가능성, 불가능 사유와 필요한 동의를 표시한다.

### 5.7 Risk Transfer Guard

원 기사의 위험을 줄이기 위해 수신 기사에게 위험을 전가하는 물량이관을 막는 하드 제약이다. 최소한 다음 조건을 검사한다.

- 수신 기사의 이관 후 Safety Budget이 최소 안전범위를 유지한다.
- 수신 기사의 적재·작업용량을 넘지 않는다.
- 허용된 종료시각과 배송 시간창을 지킨다.
- 수신 기사의 권역·차량·업무 호환성이 있다.
- 필요한 경우 수신 기사 동의가 거절 상태가 아니다.

불가능한 후보도 비교 화면에 남기고 평이한 언어로 이유를 설명한다.

### 5.8 Two-Key Consent

기본 상태에서 계획을 실제로 변경하려면 다음 두 단계가 필요하다.

1. 영향받는 기사가 근거와 효과를 확인하고 동의한다.
2. 관리자가 수신 기사 영향, ETA, 고객영향을 확인하고 승인한다.

기사 동의 없이 관리자가 강제로 승인하는 흐름은 MVP에 포함하지 않는다. 긴급조치나 법적 예외는 별도 정책이 승인되기 전까지 지원하지 않는다.

## 6. 대표 데모 시나리오

모든 시나리오는 개인식별정보가 없는 결정론적 합성 fixture로 만든다. 현재 세 대표 fixture는 원본 공공데이터 파일과 연결되지 않은 전부 `mock`인 Demo다. 향후 `public-data-derived`를 사용하려면 데이터셋 ID·공식 URI·버전·라이선스·원본 SHA-256·변환기 버전을 필드별로 추적한다.

### 6.1 시나리오 A — 우천·경사 빌라·장시간 작업

- 위치 맥락: 관악구를 모사한 언덕·골목·빌라 밀집 권역
- 근무 맥락: 누적 9.4시간, 긴 연속작업
- 환경: 강수 증가, 시야·노면 조건 악화
- 작업: 계단·도보 비중과 남은 배송량이 큼
- 목표 장면: 52분 후 17번째 남은 배송지에서 임계치 초과 예상
- 주요 비교: 휴식, 8건/12건 이관, 순서변경, 안전경로, 묶음안
- 핵심 검증: 12건 이관 차단, 8건 이관 허용, 기사 동의와 관리자 승인 후 계획 갱신

위 수치는 안전모델과 fixtures 테스트에서 재현될 때 확정한다.

### 6.2 시나리오 B — 폭염·중량물·계단 배송

- 환경: 폭염과 높은 체감온도
- 작업: 중량·부피가 큰 물량과 계단 배송 집중
- 근무 맥락: 회복이 부족한 연속 작업
- 목표 장면: ETA 손실을 최소화하는 빠른 후보보다 휴식 또는 Safe Delay가 안전 제약상 우선되는 이유 표시
- 핵심 검증: 휴식이 Budget을 회복시키고 결측 환경입력이 신뢰도를 낮추는지 확인

### 6.3 시나리오 C — 초보 기사·낯선 권역·야간

- 기사 맥락: 해당 권역 경험이 적은 신규 기사 fixture
- 환경: 야간, 좁은 골목과 주차·후진 노출
- 작업: 시간창이 다른 여러 배송지
- 목표 장면: 단순 물량균형보다 권역 호환성과 안전경로가 중요한 이유 표시
- 핵심 검증: 익숙도 저하가 Budget을 개선하지 않으며 순서변경과 안전경로가 시간창을 지키는지 확인

## 7. 히어로 루프와 상태 전이

### 7.1 정상 상태 전이

| 순서 | 상태 | 시스템 행동 | 사용자 행동 | 다음 상태 |
|---:|---|---|---|---|
| 1 | `BASELINE_EVALUATED` | 현재 계획의 Budget·초과·근거 고정 | 없음 | `CANDIDATES_GENERATED` |
| 2 | `CANDIDATES_GENERATED` | 개입 후보와 candidate ID 기록 | 없음 | `CANDIDATES_EVALUATED` |
| 3 | `CANDIDATES_EVALUATED` | 제약·전후 효과·추천 결과 기록 | 후보 비교 | `RIDER_REVIEW_REQUIRED` |
| 4 | `RIDER_REVIEW_REQUIRED` | 기사에게 동일 근거와 효과 전달 | 검토 시작 | `RIDER_RESPONSE_PENDING` |
| 5 | `RIDER_RESPONSE_PENDING` | 기사별 응답과 시각 기록 | 동의·수정 요청·거절 | 응답에 따라 분기 |
| 6 | `RIDER_CONSENTED` | 모든 필수 동의 확인 | 관리자 검토 요청 | `ADMIN_APPROVAL_REQUIRED` |
| 7 | `ADMIN_APPROVAL_REQUIRED` | 전후·ETA·형평성·고객안내 표시 | 승인·보류·수정 | 승인 시 `APPROVED` |
| 8 | `APPROVED` | 선택 candidate와 승인 스냅샷 잠금 | 없음 | `REVALIDATING` |
| 9 | `REVALIDATING` | 최신 plan version·동의·안전 제약 재검증 | 없음 | 통과 `APPLYING_PLAN`, 변화 `REVALIDATION_REQUIRED` |
| 10 | `APPLYING_PLAN` | 계획과 고객안내 요청의 원자 교체 시도 | 없음 | 성공 `APPLIED`, 실패 `APPLY_FAILED` |
| 11 | `APPLIED` | 실제 적용 plan version 기록 | 결과 확인 | `NOTICE_RECORDED` |
| 12 | `NOTICE_RECORDED` | 실제 적용 ETA 기반 안내와 근거 기록 | 없음 | `CLOSED` |
| 13 | `CLOSED` | 적용 결과와 감사 event 제공 | 필요 시 새 결정 시작 | 새 `decisionId` |

### 7.2 기사 응답 분기

- 동의: `RIDER_CONSENTED`로 이동한다.
- 수정 요청: `MODIFICATION_REQUESTED`로 이동하고 요청 범위 안에서 후보를 다시 계산한다. 새 후보는 다시 기사 검토를 받아야 한다.
- 거절: `RIDER_DECLINED`로 이동하고 비징벌적으로 다른 후보를 재계산한다. 거절한 동일 후보를 자동 재요청하지 않는다.
- 응답 대기: 기존 계획을 조용히 변경하지 않는다. 요청 또는 마지막 동의에서 10분이 지나면 `RIDER_CONSENT_EXPIRED`로 이동하고 최신 입력에서 새 후보와 동의를 생성한다.

### 7.3 관리자 분기

- 승인: 승인 당시의 결정론적 입력·출력 스냅샷을 잠근 후 계획 적용을 시작한다.
- 보류: `ADMIN_HELD` 상태에서 사유를 기록하고 계획을 변경하지 않는다.
- 반려 또는 수정: `ADMIN_MODIFICATION_REQUESTED` 상태로 이동하고 후보를 다시 계산한다. 기사에게 미치는 영향이 바뀌면 재동의를 받아야 한다.

### 7.4 실패와 폴백

- 데이터 로딩 실패: `DATA_ERROR`와 누락된 원천을 표시한다.
- 일부 데이터 결측: 계산 가능한 경우 신뢰도를 낮춰 결과를 제공하되 결측 목록을 노출한다.
- 개입 생성 실패: 현재 예측은 유지하고 `OPTIONS_ERROR`를 표시한다.
- 안전한 후보 없음: `NO_SAFE_OPTION`을 표시하고 Safe Delay 또는 물량감축을 명시적으로 요청한다.
- Upstage 실패: 수치와 추천은 유지하고 결정론적 템플릿 설명으로 전환한다.
- 계획 적용 실패: 원래 계획 또는 마지막 확정 계획을 유지하고 `APPLY_FAILED`를 감사기록에 남긴다.
- 데모 Live 실패 또는 전체 입력 계약 미충족: 부분 Live 필드를 Demo와 섞지 않고 Demo fixture 타임라인 전체를 `FALLBACK`으로 선택하며, 관리자·기사 화면에 `Demo fixture · Weather Fallback`을 유지한다.

어떠한 실패도 성공 상태처럼 보이게 하거나 실제 반영되지 않은 계획을 적용 완료로 표시해서는 안 된다.

## 8. 기능 요구사항

### FR-01 데이터 상태와 출처

시스템은 기사·작업·날씨·지역·경로 입력의 출처, 최신시각, 결측 여부와 `live/mock/error/loading/fallback` 상태를 제공해야 한다.

### FR-02 배송지별 Safety Budget 예측

현재 상태와 남은 배송계획을 입력받아 현재 Budget과 배송지별 예상 Budget 타임라인을 반환해야 한다.

### FR-03 Time-to-Breach

예측 구간의 첫 임계치 초과 예상 시각, 남은 시간, 배송지 순번과 식별자를 반환해야 한다. 초과가 없으면 명시적인 무초과 상태를 반환해야 한다.

### FR-04 설명 가능성

결과는 정렬된 위험 기여요인, 신뢰도, 결측 입력과 사용한 모델·설정 버전을 포함해야 한다.

### FR-05 개입 후보 비교

다섯 개 개입 유형과 호환 가능한 묶음 후보를 생성하고 안전효과, ETA, 복잡도, 고객영향, 형평성, 실행 가능성을 동일한 계약으로 비교해야 한다.

### FR-06 안전 우선 순위화

실행 불가능하거나 안전 제약을 위반하는 후보를 추천하지 않아야 한다. 실행 가능한 후보 안에서만 안전효과, 지연비용, 형평성, 운영복잡도를 비교해야 한다.

### FR-07 Risk Transfer Guard

모든 물량이관 후보는 수신 기사의 이관 후 Budget, 용량, 시간창, 종료시각과 호환성을 검사해야 한다. 불가능 후보는 이유와 함께 표시해야 한다.

### FR-08 기사 검토와 응답

기사 앱은 관리자와 같은 결정 ID에 연결된 원인, 효과, 지연, 형평성을 보여주고 동의·수정 요청·거절을 제공해야 한다.

### FR-09 관리자 승인

관리자는 기사 응답, 조정 전후 결과, 수신 기사 영향, ETA와 고객안내 초안을 확인한 후 승인·보류·수정을 선택할 수 있어야 한다.

### FR-10 계획 갱신

승인된 결정만 경로, 배송순서, 기사별 작업목록, ETA에 반영해야 한다. 반영은 성공 또는 실패가 명시적인 원자적 작업으로 기록되어야 한다.

관리자 `경로` 탭은 불변 일일 스냅샷의 기준 계획과 운영 workspace의 활성 계획을 같은 기사 범위에서 비교해야 한다. 승인 전에는 `현재 계획 유지`를 표시하고 기준 계획만 사용한다. `NOTICE_RECORDED` 이후에는 적용 전·후 계획 버전, 남은 배송 수, 배송순서와 예상 종료시각을 표시하며 Kakao 경로 미리보기는 적용된 활성 계획을 읽는다. 배송지별 ETA는 같은 활성 계획·고객안내·CSV에 유지한다. 지도 공급자 결과는 이미 적용된 계획을 다시 계산하거나 덮어쓰지 않는다.

### FR-11 고객안내

갱신된 각 합성 배송지의 적용 ETA를 입력으로 사용해 기사 개인정보나 책임 표현 없이 안전운영에 따른 변경 안내 초안을 생성해야 한다. 초안은 `PREVIEW_ONLY`와 실제 미발송 상태를 명시하고 JSON 및 CSV로 내보내야 한다.

### FR-12 감사기록

입력·모델버전·후보·불가능 사유·기사 응답·관리자 결정·적용 결과·고객안내·전후 지표를 하나의 결정 ID로 추적해야 한다.

### FR-13 Upstage 근거 계층

합성 안전문서를 파싱하고 허용된 규칙 필드를 구조화·검증한 뒤, 제공된 수치와 인용문만으로 기사·관리자·고객용 설명을 생성해야 한다. LLM 출력은 결정론적 결과를 변경할 수 없어야 한다.

### FR-14 Near-miss 피드백

기사는 정차 상태에서 카테고리, 심각도, 선택 메모와 거친 위치를 신고할 수 있어야 한다. 신고는 검증 후 미래의 지역화 위험에만 반영되고 신고 기사에게 즉시 불이익을 주지 않아야 한다.

### FR-15 데모 제어

대표 fixture를 한 번에 로드하고, 단계 이동과 초기화가 가능해야 한다. Live 실패 시 폐루프를 중단하지 않고 명시적인 Demo fixture로 전환해야 한다.

### FR-16 다지역 지도 projection

시스템은 지역·허브·기사·계획·decision과 위치 최신성 상태를 검증된 지도 projection으로 제공해야 한다. 지도와 지원 큐는 같은 식별자를 사용하고, 저배율에서는 개별 기사와 정밀 위치 대신 집계를 표시해야 한다. 이 projection은 Safety 수치나 추천을 계산하지 않는다.

### FR-17 기사 PWA 목표

기사 PWA는 현재 위치·다음 배송지·Safe-until과 주요 행동을 첫 화면에서 제공하고, 위치 권한 거절·stale·오프라인·지도 실패 시 마지막 승인 계획과 명시적 fallback으로 전환해야 한다. ADR-124에 따라 사용자가 `내 위치 표시`를 누른 경우에만 브라우저 위치 권한을 요청하고, 좌표는 현재 페이지의 카카오 지도 2D 택배차 상단 마커에만 사용한 뒤 페이지 이탈 시 폐기한다. 마커는 지도 확대 단계와 폭에 맞춰 크기가 달라지고, 첫 좌표 이후 새 기기 관측 사이를 부드럽게 이동하되 화면 보간값을 위치 데이터로 저장하지 않아야 한다. G3-B는 manifest와 정적 service worker를 제공하고, 승인·적용된 합성 계획만 30분간 최소 필드로 저장한다. 실제 인증·푸시·위치 서버 동기화는 포함하지 않는다.

ADR-125에 따라 기사 앱과 관제는 같은 기사 ID의 서버 기록과 같은 가상 도로 이동 함수를 사용해야 한다. 두 화면은 현재 점수와 예상 최저 점수를 구분해 같은 값으로 표시하고, 지도 축척을 근거리 탑차·권역 축소 탑차·광역 상태 점의 세 단계로 바꿔야 한다. 기사 본인이 켠 기기 위치는 계속 기사 화면 안에서만 사용하며 관제와 동기화된 위치로 주장하지 않는다.

### FR-18 결정론적 Demo 이동

관리자는 선택한 권역에서 24명 합성 fixture의 단기 위치 이벤트를 재생·일시정지·한 단계 이동·초기화할 수 있어야 한다. 화면은 `Demo movement`와 `Live 0명`을 고정 표시하며 stale·offline은 움직이지 않고 연결 복구는 새 합성 관측 이후에만 표시한다. 이동 타임라인은 Safety 계산, 추천, 기사 동의·관리자 승인과 감사기록을 변경할 수 없다.

### FR-19 지도 부하 보호

시스템은 공개 Demo 기본 24명과 진단용 96·240명 합성 profile을 재현해야 한다. 전국 화면은 개별 기사 위치를 표시하지 않고, 권역 화면은 최대 80명의 합성 상태를 표시하되 동시에 그리는 경로를 24개로 제한한다. 제한된 경로는 기사 선택 시 상세 화면에서 확인할 수 있어야 하며 지원 decision을 삭제하거나 Safety 결과를 변경해서는 안 된다.

### FR-20 선택형 Demo 2.5D 경사 맥락

관리자 활성 decision에서만 기본 2D와 같은 decision·plan·route point·Safety 수치를 읽는 공급자 독립 `Demo 2.5D`를 사용자가 선택해 열 수 있다. 합성 고도·경사와 `Live 0명`을 고정 표시하고, 위험은 높이가 아니라 패턴·텍스트로 설명한다. 계약·지도 오류 또는 수치 불일치 시 입체 보기를 차단하고 기본 2D와 구조화 수치 대안으로 복귀한다. 기사 PWA와 실제 지도·위치 계약은 변경하지 않는다.

### FR-21 역할별 서비스 탭

관리자 서비스는 `일일 운영 / 지원 상황 / 경로 / 개입 검토 / 감사·내보내기` 다섯 화면을 하나의 운영 workspace 상태로 연결해야 한다. 지원 상황에서 decision을 선택하면 같은 decision ID의 개입 검토로 이동하고, 경로·감사 화면도 같은 스냅샷을 사용해야 한다. 기사 서비스는 `운행 / 안전지원 / 내 정보` 세 탭으로 고정하고, 직접 받은 decision 링크는 안전지원 탭에서 시작하되 운행 경로와 데이터 경계를 왕복할 수 있어야 한다. 탭 전환은 Safety 계산·동의·승인·저장 상태를 초기화하지 않는다.

지원 상황 탭은 전체 합성 기사 위치와 `완료/전체 배송 건수` 진행률을 같은 평가시각의 지도 스냅샷으로 표시한다. 지원 대상 마커를 선택하면 해당 decision의 개입 검토로 이동한다. 실제 GPS feed가 없는 현재 범위에서는 `합성 스냅샷 · Live 0명`과 `실시간 아님`을 고정 표시하며, 합성 위치를 Live 또는 현재 정밀 위치처럼 표현하지 않는다.

## 9. 비기능 요구사항

### NFR-01 결정론과 재현성

동일한 입력, 설정 버전과 시각 기준에서 핵심 계산은 동일한 결과를 반환해야 한다. 세 대표 fixture에는 정확한 예상 출력 테스트를 둔다.

### NFR-02 검증 가능성

핵심 모델은 경계값, 단조성, 회복, 결측, 위험전가와 AI 숫자 불변 테스트를 통과해야 한다.

### NFR-03 접근성

- 키보드만으로 관리자 개입 큐와 승인 모달을 사용할 수 있어야 한다.
- 관리자 세로 탭은 위·아래·Home·End, 기사 하단 탭은 좌·우·Home·End 키로 이동할 수 있어야 한다.
- 포커스가 보여야 한다.
- 상태를 색상만으로 구분하지 않아야 한다.
- 기사 화면의 주요 터치영역은 최소 44px이어야 한다.
- reduced-motion 설정을 존중해야 한다.
- 데모 빌드의 Lighthouse 접근성 목표는 90 이상이다.

### NFR-04 반응형 화면

- 관리자: 1440×900, 1280×720
- 기사: 390×844, 360×800

각 화면에서 핵심 결정 정보와 주요 행동이 잘리거나 스크롤 뒤에 숨지 않아야 한다.

### NFR-05 복구 가능성

네트워크, Upstage, 외부 데이터 오류가 전체 데모를 중단시키지 않아야 한다. Fallback은 정상 Live 상태와 시각적으로 구분되어야 한다.

### NFR-06 개인정보 최소화

fixtures, 로그, 스크린샷과 테스트 산출물에 실제 개인식별정보를 포함하지 않는다. 역할별로 필요한 최소 파생정보만 제공한다.

### NFR-07 설명 일관성

기사, 관리자, 고객 설명의 모든 수치와 결정 상태는 동일한 결정론적 입력 JSON 또는 적용 결과에 존재해야 한다.

### NFR-08 성능 목표

로컬 데모 fixture 기준으로 예측과 후보 비교는 사용자 행동 후 1초 이내에 결과를 표시하는 것을 목표로 한다. Upstage 응답을 기다리는 동안 결정론적 결과와 UI를 차단하지 않는다.

### NFR-09 감사 가능성

각 상태 전이에는 결정 ID, 시각, 행위자 또는 시스템 원인, 이전·다음 상태와 입력/출력 버전을 기록한다.

## 12. 수용기준

### AC-01 대표 폐루프

시나리오 A를 초기화한 뒤 예측, 원인, 후보 비교, 12건 이관 차단, 기사 동의, 관리자 승인, 계획·ETA 갱신, 고객안내와 전후 지표를 하나의 결정 ID로 완료할 수 있다.

### AC-02 안전 제약

수신 기사 Budget을 최소 안전범위 아래로 내리는 후보는 ETA가 가장 짧더라도 추천 또는 적용할 수 없다.

### AC-03 동의와 승인

기사 동의가 없는 계획변경은 관리자 승인 및 적용 단계로 이동하지 않는다. 수정 요청 후 효과가 바뀐 후보는 재동의를 받는다.

### AC-04 정확한 상태

Live, Mock, Loading, Error와 Fallback이 데이터와 화면에서 명확히 구분된다. 실패한 적용을 완료로 표시하지 않는다.

### AC-05 설명 무결성

Upstage 설명의 모든 수치가 입력 JSON에 존재하며, 설명을 변경해도 Safety Budget·실행 가능성·추천안이 바뀌지 않는다.

### AC-06 단조성과 결측

동일 조건에서 연속근무, 남은 작업량, 강수 또는 경로위험 증가가 Budget을 개선하지 않는다. 휴식 증가가 회복을 악화하지 않고, 결측 증가가 신뢰도를 높이지 않는다.

### AC-07 접근성과 반응형

지정한 관리자·기사 해상도에서 폐루프의 주요 행동을 수행할 수 있고, 키보드·포커스·비색상 상태표현·44px 터치 기준을 충족한다.

### AC-08 데모 복구

Upstage 또는 Live 데이터 실패 상태에서도 Demo fixture 표시와 함께 3분 폐루프를 끝까지 진행하고 초기 상태로 리셋할 수 있다.

### AC-09 비징벌성

관리자 및 기사 UI, 생성 문구와 감사로그에 순위, 저성과, 비난, 거절에 대한 불이익을 암시하는 표현이 없다.

### AC-10 결과 표현

화면, 보고서, 발표자료에서 결과를 사고확률이나 실제 사고감소로 표현하지 않고 시뮬레이션·운영 위험지수로 정확히 표시한다.

## 15. 확정된 결정

- 하나의 폐루프를 기능 수보다 우선한다.
- 결과를 사고확률이 아닌 운영 위험지수와 Safety Budget으로 표현한다.
- 안전을 ETA·비용보다 먼저 적용하는 하드 제약으로 둔다.
- 관리자 웹과 기사 반응형 모바일 웹이 동일한 결정 근거를 공유한다.
- 계획 변경은 기사 동의와 관리자 승인을 기본으로 한다.
- 관리자는 Calm Control Tower, 기사는 Field-first Human UI 방향을 사용한다.
- 최종 공간운영 확장은 `design-v2.0.0`과 `geospatial-pwa-plan-v1.0.0`을 따르며 합성 2D 지도부터 구현한다.
- 대표 시나리오는 우천·경사·장시간 작업으로 한다.
- 실제 고객 발송과 별도 고객 앱은 MVP에서 제외한다.

## 16. 미결사항

- 실제 인증 도입 시 원 기사·수신 기사의 계정·권한 연결 방식
- 기사 응답 재알림 방식과 MVP 밖 긴급상황 정책
- 외부 TMS 연동 시 트랜잭션·보상 작업 방식
- Near-miss 위치 정밀도, 검증자와 시간감쇠 규칙
- Kakao Maps 합성 Demo 이후의 실시간 위치·주소·길찾기·3D·PWA 서버 동기화 범위
- Upstage 반복 부하에서의 retry·회로차단 운영 수치
- 호환 개입 묶음을 화면에 노출할 최종 후보 수와 시나리오별 표시값

미결사항은 관련 후속 문서가 `Approved`가 되기 전까지 구현 동작으로 간주하지 않는다.
