# SafeRoute AI 개인정보·책임 있는 AI 정책

## 문서 상태

- 상태: Approved
- 담당: 팀 안전빵
- 최종 갱신: 2026-08-08
- 정책 버전: `privacy-ai-v1.5.0`
- 상위 문서: `AGENTS.md`, `docs/product-spec.md`, `docs/data-contracts.md`, `docs/safety-model.md`, `docs/intervention-policy.md`

## 1. 목적

이 문서는 SafeRoute AI가 기사·관리자·고객 관련 데이터를 어떤 목적으로 최소한으로 사용하고, 누구에게 무엇을 보여주며, Upstage를 포함한 AI 계층의 권한을 어디까지 제한할지 정의한다.

핵심 원칙은 다음과 같다.

> SafeRoute는 기사를 감시하거나 평가하는 시스템이 아니라, 위험한 배송계획을 투명한 동의 아래 변경하는 안전운영 도구다.

## 2. 적용 범위와 법적 한계

이 정책은 다음에 적용한다.

- 관리자 웹
- 기사 반응형 모바일 웹
- 최종 제품의 기사 PWA와 다지역 관리자 지도
- 고객안내 미리보기
- Safety Budget과 개입 엔진
- Upstage Document Parse, Information Extract와 Solar
- Near-miss 신고·검증·지역기억
- 테스트, fixtures, 로그, 스크린샷, 보고서와 데모 영상

### 2.1 G5-A 합성 공간정보 경계

G5-A의 거리·고도·경사·경로점은 실제 기사 위치나 지형 관측이 아니라 `MOCK + isDemo` 합성 계약이다. 관리자 장면은 활성 decision의 설명에만 사용하고 원시 위치·정밀 궤적·주소·건물·생체정보를 추가 수집하거나 저장하지 않는다. A.X·K-EXAONE·Upstage를 포함한 생성형 AI는 이 수치와 geometry를 만들거나 변경하지 않는다. `Demo 2.5D`, `Live 0명`, 합성 고도 표시를 제거할 수 없고, 계약 불일치 시 Live로 승격하지 않고 2D Fallback으로 전환한다.

이 문서는 제품 내부 가드레일이며 개인정보·노무·산업안전·AI 관련 법률 준수를 보증하는 법률문서가 아니다. 실제 기사·고객 데이터를 사용하는 파일럿 전에는 적용 지역과 운영형태에 맞는 별도 법률·노무·보안 검토가 필요하다.

## 3. MVP 데이터 모드

### 3.1 기본 원칙

2026-08-14 본선 MVP는 다음 데이터만 사용한다.

- 개인식별정보가 없는 결정론적 합성 fixture
- 허용된 공개 데이터에서 파생된 비개인 특징
- 합성 안전운영 매뉴얼과 합성 사고·Near-miss 문서
- 역할 기반 사용성 테스트에서 별도 동의받은 최소 응답

MVP에 실제 기사 이름, 전화번호, 전체 주소, 정밀 개인 궤적, 원시 생체정보, 얼굴·음성·주행 영상을 입력하지 않는다.

### 3.2 Live 표시 제한

외부 날씨·지도·Upstage API가 실제로 응답해도 기사·배송 fixture가 합성이면 전체 시나리오는 `Demo`다. 일부 API가 Live라는 이유로 전체 결과를 Live 운영결과처럼 표시하지 않는다.

```text
synthetic courier or synthetic plan present
→ overall scenario mode = DEMO
```

### 3.3 실데이터 파일럿 잠금

다음 조건이 모두 충족되기 전에는 실제 기사·고객 데이터를 받는 기능을 활성화하지 않는다.

- 수집 목적과 필드별 필요성 승인
- 고지·동의 또는 적절한 처리근거 검토
- 역할별 접근권한 승인
- 보존·삭제·내보내기 절차 구현
- 공급자 데이터 처리조건 검토
- 보안 위협모델과 침해대응 절차 검토
- 기사 이의제기·정정·철회 절차 구현
- 원시 생체정보를 사용하지 않는 기본 설계 확인
- 관리자 화면에서 감시·징계 사용을 막는 운영정책 승인
- 파일럿 중단 및 데이터 삭제 계획 승인

환경변수 하나나 화면 토글만으로 이 잠금을 해제하지 않는다.

## 4. 개인정보·운영 데이터 원칙

### 4.1 목적 제한

데이터는 다음 목적에만 사용한다.

1. 남은 배송계획의 운영상 안전여유 계산
2. Time-to-Breach와 기여요인 설명
3. 안전한 개입 후보 생성·검사
4. 기사 동의와 관리자 승인
5. 승인된 계획·ETA·고객안내 갱신
6. 결정 재현과 안전성 평가
7. 검증된 Near-miss의 미래 지역위험 반영

다음 목적으로 재사용하지 않는다.

- 기사 순위와 성과평가
- 징계, 계약해지, 임금·인센티브·보험 판단
- 거절 성향 또는 순응도 프로파일링
- 생산성 압박과 작업량 상향
- 마케팅·광고·데이터 판매
- 동의하지 않은 생체·건강 추론

### 4.2 최소 수집

각 필드는 다음 질문을 통과해야 한다.

- P0 폐루프에 실제로 필요한가?
- 더 거친 값이나 파생값으로 대체할 수 없는가?
- 사용자가 이 값의 목적을 이해할 수 있는가?
- 관리자에게 보여주지 않고 엔진에서만 처리할 수 없는가?
- 보존하지 않고 일시 처리할 수 없는가?

하나라도 답이 불명확하면 기본적으로 수집하지 않는다.

### 4.3 정확성·정정 가능성

- 데이터 출처와 최신시각을 표시한다.
- 사용자가 직접 입력한 값과 자동 수집한 값을 구분한다.
- 결측·오류·추정값을 실제 관측값처럼 표시하지 않는다.
- 기사에게 본인 관련 운영 입력과 파생 결과를 확인·정정 요청할 경로를 제공한다.
- 정정 전 계산과 정정 후 계산을 감사기록으로 구분한다.

### 4.4 비보복

다음 행동은 기사에게 불이익을 주는 신호로 사용하지 않는다.

- 개입안 거절
- 수정 요청
- 이의제기
- Near-miss 신고
- 선택형 센서·웨어러블 미사용
- 데이터 정정·삭제·접근 요청

이 행동의 횟수, 비율 또는 사유를 관리자 KPI나 기사 프로파일에 만들지 않는다.

## 5. 데이터 분류

### 5.1 허용되는 운영 데이터

| 범주 | 예시 | 관리자 표시 | AI 전송 | MVP 보존 |
|---|---|---:|---:|---:|
| 합성 기사 상태 | 근무·연속작업 시각, 차량 종류 | 파생값 중심 | 최소 JSON | fixture |
| 합성 작업량 | 남은 건수, 중량·계단 집계 | 허용 | 집계값만 | fixture |
| 날씨 | 강수, 체감온도, 시정 | 허용 | 필요 시 근거값 | 캐시 가능 |
| 지역위험 | 경사, 좁은 길, 검증된 집계 | 허용 | 코드·근거만 | 버전 데이터 |
| 안전결과 | Budget, Time-to-Breach, 기여도 | 허용 | 불변 JSON | 결정기록 |
| 동의 상태 | 대기·동의·수정·거절 | 해당 결정에서만 | 원칙적 미전송 | 결정기록 |
| 고객영향 | 변경 ETA, 영향 건수 | 허용 | 비식별 값만 | 결정기록 |

### 5.2 제한 데이터

실데이터 파일럿에서도 별도 승인과 최소화가 필요한 데이터다.

- 정확한 현재 위치
- 상세 배송주소
- 자유문 Near-miss note
- 기사 자기점검 응답
- DMS에서 파생된 상태 factor
- 웨어러블에서 파생된 상태 factor
- 관리자·기사 자유문 결정 사유

제한 데이터는 역할·목적·보존기간을 별도로 승인해야 한다.

### 5.3 금지 데이터

- 주민번호, 계좌, 개인 연락처
- 기사·고객의 실제 이름이 포함된 fixture·로그·프롬프트
- 원시 심박, HRV 파형, 산소포화도, 수면단계
- 얼굴·음성·주행 영상 원본
- 장기 정밀 위치궤적
- 의료진이 아닌 시스템의 질병·장애 추론
- 노동조합·정치·종교 등 안전운영과 무관한 특성
- 과거 거절 횟수, 순응도, 기사별 위험 순위
- 고객 메시지에 기사 건강·동의·거절 정보

알 수 없는 외부 필드는 데이터 계약 검증에서 거부한다.

## 6. 역할과 접근권한

### 6.1 기사

본인에 대해 다음을 볼 수 있다.

- 사용된 운영 입력과 최신시각
- Safety Budget 범위, 밴드와 타임라인
- Time-to-Breach
- 주요 기여요인, 신뢰도, 결측·가정
- 본인에게 영향을 주는 후보와 전후 결과
- 물량이관 시 상대 기사 Guard 통과 여부
- 본인의 동의·수정·거절·이의제기 기록
- 어떤 데이터가 관리자와 AI에 전달되는지

상대 기사의 상세 Budget, 작업목록, 위치 또는 개인 상태는 보여주지 않는다. `상대 기사도 최소 안전기준을 통과함`처럼 필요한 결과만 제공한다.

### 6.2 허브 관리자

업무 수행에 필요한 다음 파생정보만 볼 수 있다.

- 지원이 필요한 합성 또는 운영 ID
- Time-to-Breach와 예상 배송지·구간
- 위험 기여요인과 결측·신뢰도
- 개입 전후 결과와 수신 기사 Guard 판정
- 기사 응답 상태와 관리자 승인 상태
- 변경 ETA, 고객영향과 감사기록
- 익명·집계된 Near-miss 지역기억

다음은 볼 수 없다.

- 원시 생체정보
- 선택형 센서의 상세 원본
- 장기 정밀 이동궤적
- 다른 기사와의 순위·점수 비교
- 거절·신고 횟수 기반 프로파일
- 안전운영과 무관한 개인특성

### 6.3 시스템 운영자·개발자

- 기본 로그에는 비식별 ID와 기술 상태만 기록한다.
- 운영자도 실제 개인정보를 볼 수 있다는 전제로 설계하지 않는다.
- 디버그 모드는 제품 환경에서 기본 비활성화한다.
- 전체 요청·응답 본문 로깅을 금지한다.
- 지원 목적으로 데이터 접근이 필요한 실파일럿에서는 사유·기간·접근자를 감사기록에 남긴다.

### 6.4 고객

고객안내에는 다음만 포함한다.

- 변경 전·후 ETA 중 필요한 값
- 안전운영에 따른 조정이라는 일반적 이유
- 배송상태 또는 문의 경로

기사 ID, 이름, 건강·피로·동의·거절·다른 배송 고객 정보는 포함하지 않는다.

## 7. 기사 권리와 사용자 통제

### 7.1 알 권리

기사 반응형 모바일 웹은 다음을 평이한 한국어로 설명한다.

- 어떤 데이터가 사용되는가
- 각 데이터가 계산에 어떤 역할을 하는가
- 관리자에게 무엇이 보이는가
- Upstage에 어떤 정보가 전달되는가
- 선택형 데이터 없이도 서비스를 사용할 수 있는가
- 결과가 사고확률이나 성과점수가 아니라는 점

### 7.2 동의·수정·거절

- 동의 전에 원인, 효과, ETA와 작업변화를 제공한다.
- 수정 요청과 거절을 동의와 동등한 수준으로 접근 가능하게 한다.
- 거절 사유는 선택 입력이다.
- 동의는 특정 decisionId·candidateId·planVersion에 한정한다.
- 중요한 조치·수치·영향 변경 시 재동의를 받는다.
- 동의하지 않은 조치를 관리자가 강제로 승인할 수 없다.

### 7.3 이의제기

기사는 다음에 대해 이의제기할 수 있다.

- 잘못된 근무·휴식·작업량 입력
- 잘못된 경로·지역위험 정보
- Safety Budget 설명 또는 결측 처리
- 본인의 동의 상태
- 계획 적용 결과
- 관리자에게 노출된 정보

이의제기 중 자동 불이익을 주지 않는다. 결과가 바뀌는 정정은 새 계산·결정 버전으로 기록한다.

### 7.4 선택형 센서

- DMS·웨어러블은 MVP 필수 입력이 아니다.
- 사용하지 않아도 신뢰도 감점을 주지 않는다.
- 사용할 경우 원시값을 저장·표시하지 않고 목적에 필요한 파생 factor만 받는다.
- 선택 철회 후 새 계산에서는 해당 factor를 사용하지 않는다.

## 8. 위치정보 정책

### 8.1 경로계산

정확 위치가 필요한 경우 메모리 내 또는 단기 처리에만 사용하고 장기 기사 궤적으로 보존하지 않는다. 로그, 스크린샷과 AI 프롬프트에서 정확 좌표를 제거한다.

### 8.2 관리자 지도

관리자 지도는 운영상 필요한 현재 구간·배송지 상태를 보여줄 수 있지만, 기사 개인의 장기 재생·추적 기능을 제공하지 않는다.

다지역 지도는 전국·권역과 낮은 확대 수준에서 기사별 위치를 군집·집계한다. 가명 기사 ID와 현재 위치는 선택한 허브의 현재 지원 decision을 처리하는 데 필요한 범위에서만 노출할 수 있다. 속도·체류·경로이탈을 기사 성과나 징계 지표로 만들지 않는다.

### 8.2.1 G1 합성 위치 잠금

G1 위치 projection은 모두 결정론적 `MOCK`, `isDemo=true`다. 실제 기사·고객·차량 식별자, 실제 배송주소와 운영 궤적을 사용하지 않는다. 합성 위치 event는 Safety 엔진 입력이나 실제 사고감소 증거가 아니며, Demo 마커 이동을 Live 추적으로 표시하지 않는다.

### 8.2.2 Live 위치 잠금

정확한 Live 현재 위치는 5.3의 제한 데이터다. 수집 목적, 역할별 접근, 정밀도·갱신주기·메모리 보존시간·삭제, 기사 고지·정정·철회, 공급자 처리조건과 보안 검토가 모두 승인되기 전에는 활성화하지 않는다. 환경변수·지도 SDK·브라우저 권한 요청만으로 이 잠금을 해제하지 않는다.

ADR-124는 이 잠금의 좁은 예외로 기사 본인이 버튼을 눌러 현재 화면에서만 확인하는 기기 위치 표시를 승인한다. 좌표와 정확도는 페이지 메모리에만 존재하며 서버·D1·브라우저 영구 저장소·AI 입력·일반 로그·감사기록·관리자 화면으로 전송하지 않는다. 페이지를 벗어나거나 컴포넌트가 해제되면 `clearWatch`로 관찰을 끝내고 메모리 상태를 폐기한다. 서버 동기화·백그라운드 위치·관리자 공유·장기 궤적은 계속 잠금 상태다.

### 8.2.3 Kakao Maps Demo 표시 경계

- 관리자와 기사 Kakao Maps JavaScript SDK에는 `MapAdapter`가 검증한 결정론적 합성 위도·경도와 합성 경로만 전달한다. 기사 compact map도 같은 decision에서 파생한 합성 세 지점만 사용한다.
- 실제 기사·고객 식별자, 배송주소, 전화번호, 생체정보, Live GPS와 장기 이동궤적은 전달하지 않는다.
- 브라우저용 JavaScript 플랫폼 키는 공개 클라이언트 식별자이므로 서버 비밀키처럼 취급하지 않지만, 저장소에 커밋하지 않고 Kakao 앱의 허용 도메인으로 제한한다.
- 지도 SDK 요청과 렌더링 상태를 국내 AI 모델 입력, 일반 로그, Safety 계산이나 감사 결과로 재사용하지 않는다.
- SDK 오류·차단·키 미설정·오프라인은 기사 권리나 지원 decision을 막지 않으며 같은 합성 데이터의 schematic 지도와 구조화 목록으로 전환한다.
- 이 승인은 실제 위치 수집·브라우저 위치 권한·주소 검색·길찾기·TMS 연동 또는 유료 지도 계약 승인이 아니다.

### 8.2.4 Kakao Mobility 합성 길찾기 경계

- Directions API에는 서버에 고정된 결정론적 합성 현재 위치·휴식 지점·다음 배송지만 전달한다. 브라우저 요청의 좌표·주소·기사 식별자는 받지 않는다.
- REST API 키는 서버 전용 `KAKAO_MOBILITY_REST_API_KEY`로만 관리하고 브라우저 bundle, 응답, 로그와 산출물에 포함하지 않는다.
- 정규화된 경로선·거리·예상시간은 기사 Demo 미리보기와 Kakao Map 길찾기 링크에만 사용한다.
- 공급자 원문과 요청 ID는 저장하지 않고, 정규화 결과도 Safety 계산·기사 평가·감사 점수에 재사용하지 않는다.
- 오류·오프라인·쿼터·키 미설정은 기존 schematic 경로와 구조화 목록으로 명시적으로 복귀하며 기사 동의·거절과 관리자 승인을 막지 않는다.
- 실제 GPS·배송주소·고객정보·브라우저 Geolocation 전송은 계속 승인되지 않는다.

### 8.2.5 G4-A Demo 이동 경계

- 이동 frame은 동일 seed·기준시각에서 생성한 30초 합성 이벤트이며 `Demo movement · Live 0명`으로 표시한다.
- stale 관측을 보간하거나 offline 구간을 예측하지 않는다. 연결 복구는 새 합성 `CURRENT` 이벤트가 있는 frame 이후에만 표시한다.
- 전국 화면은 계속 지역 집계만 제공하고, 선택 권역에서만 가명 기사 8명의 단기 위치를 표시한다.
- 합성 운영 서비스의 지원 상황 탭은 근무표 평가시각과 seed에서 만든 25명의 합성 위치 및 완료·전체 배송 건수만 표시한다. 이는 이동 frame이나 실제 GPS가 아닌 고정 스냅샷이며 `합성 스냅샷 · Live 0명`과 `실시간 아님`을 함께 표시한다.
- 실제 기사 GPS, 브라우저 Geolocation, 정밀 이동궤적, 외부 TMS 위치 feed는 사용자 재승인과 별도 동의·권한·보존·접근통제 계약 없이는 수집·저장·표시하지 않는다.
- 타임라인은 브라우저 메모리에서만 재생하며 개인 장기 궤적, 일반 로그, AI 입력과 감사기록으로 저장하지 않는다.
- 이 기능은 실제 위치 수집·감시·성과평가·Live 이동을 승인하지 않는다.

### 8.3 Near-miss

- 저장·집계에는 `CoarseLocation`을 사용한다.
- 관리자에게 신고자 ID를 제공하지 않는다.
- 동일 구역의 최소 집계기준을 충족하지 않으면 개별 점 대신 `검증 대기`로 표시한다.
- 검증된 신고만 미래 지역위험에 반영한다.
- 신고 직후 신고 기사의 현재 Budget을 소급 변경하지 않는다.

GeoHash 정밀도와 최소 집계기준은 실제 지도·지역 크기를 검토한 뒤 별도 승인한다.

### 8.4 기사 PWA 위치 권한

- 위치와 알림 권한을 별도로 설명하고 묶음 동의를 사용하지 않는다.
- 위치 권한은 기사 본인이 `내 위치 표시`를 누른 뒤에만 요청하며 페이지 진입 시 자동 요청하지 않는다.
- 위치 권한 거절·철회는 불이익·실패·낮은 신뢰도 점수로 표시하지 않는다.
- 권한이 없으면 마지막 승인 계획과 `경로 위치`로 이름 붙인 schematic route를 제공한다.
- `watchPosition`의 좌표·정확도·갱신시각은 현재 페이지 메모리에서 지도 마커를 갱신하는 데만 사용하고 페이지 이탈 시 폐기한다.
- 기기 위치는 카카오 지도 SDK에 표시할 수 있지만 주소 변환, 길찾기 서버, D1, localStorage, 관리자 관제, 외부 AI에 전달하지 않는다.
- 오프라인 캐시는 마지막 `APPROVED + APPLIED` 계획만 읽기 전용으로 제공한다.
- 오래된 캐시에서 동의·승인·계획 적용을 성공으로 기록하지 않는다.
- 앱 제거·로그아웃·세션 만료 시 승인된 정책에 따라 위치·계획 캐시를 삭제한다.

#### 8.4.1 G3-B 계획 캐시 적용

- 현재 PWA는 ADR-124의 사용자 요청형 위치 권한만 사용할 수 있으며 알림·인증 권한은 요청하지 않는다.
- 캐시는 합성 `decisionId`, `planId`, `planVersion`, 저장·만료시각과 합성 기사별 남은 배송 건수만 포함한다.
- 이름·전화번호·주소·좌표·원시 생체·고객 ETA·AI 요청·응답을 저장하지 않는다.
- TTL은 30분이며 정확히 만료시각부터 `EXPIRED`로 판정해 최신 계획처럼 표시하지 않는다.
- 오프라인에서는 캐시를 읽기만 하고 동의·수정·거절·승인·적용을 성공으로 기록하지 않는다.
- `Demo 초기화`는 저장된 승인 Demo 계획도 함께 삭제한다.

## 9. Near-miss 비보복 정책

### 9.1 수집 목적

Near-miss는 골목, 계단, 주차, 미끄럼, 시야, 후진 같은 지역·작업 위험을 미래 계획에 반영하기 위해 사용한다.

### 9.2 금지

- 신고한 기사에게 즉시 위험점수 가산
- 신고 횟수를 기사 성과로 표시
- 관리자에게 신고자 식별정보 제공
- 신고하지 않은 기사를 더 안전하다고 평가
- 검증되지 않은 신고를 경로위험에 즉시 반영
- 자유문 note를 LLM 학습자료로 재사용

### 9.3 검증과 반영

```text
PENDING
→ VALIDATED | DUPLICATE | LOW_CONFIDENCE | REJECTED
→ validated aggregate
→ time decay and weather interaction
→ future localized route feature
```

신고자의 현재 결정에는 영향이 없고 다음 계획 평가부터 집계 특징으로만 사용할 수 있다.

## 10. Upstage 역할

### 10.1 허용된 역할

#### Document Parse

- 합성 또는 사용 허가된 안전운영 문서를 Markdown/HTML 구조로 변환
- 페이지·섹션 위치 보존

#### Information Extract

- 허용 목록의 안전규칙 필드 추출
- 위험유형, 적용조건, 권장행동, 출처 페이지·섹션 구조화

#### Solar

- 결정론적 JSON과 검증된 인용을 기반으로 기사 설명 생성
- 관리자 결정 메모 생성
- 고객 안전지연 안내 생성
- 일일 안전개입 요약 생성

### 10.2 금지된 역할

- Safety Budget·기여도·Time-to-Breach 계산
- 실행 가능성·Risk Transfer Guard 판정
- 추천 순위 또는 최종 조치 변경
- 누락된 수치 추정·반올림·재계산
- 제공되지 않은 문서 인용
- 기사 탓·성과·순응도 평가
- 건강상태·질병·사고확률 추론
- 사용자 동의 또는 관리자 승인 대신 수행

## 11. Upstage 입력 계약

### 11.1 원칙

Upstage에는 역할별 설명에 필요한 최소 데이터만 보낸다. 전체 도메인 객체나 데이터베이스 레코드를 그대로 전송하지 않는다.

### 11.2 허용 입력 예시

```ts
type ExplanationInput = {
  requestId: string;
  role: "COURIER" | "ADMIN" | "CUSTOMER" | "REPORT";
  language: "ko";
  dataMode: "DEMO" | "LIVE_PILOT";

  numericFacts: Array<{
    factId: string;
    label: string;
    value: number;
    unit: string;
    displayValue: string;
  }>;
  stateFacts: Array<{
    factId: string;
    label: string;
    value: string;
  }>;
  allowedCitations: Array<{
    citationId: string;
    documentTitle: string;
    page?: number;
    section?: string;
    excerpt: string;
  }>;
  prohibitedTopics: string[];
};
```

### 11.3 입력에서 제거

- 실제 기사·고객 이름과 연락처
- 정확 좌표와 전체 주소
- 원시 생체·센서 데이터
- 자유문 Near-miss note
- 다른 기사의 상세 상태
- API 키·내부 토큰·보안설정
- 설명에 필요하지 않은 전체 감사로그

### 11.4 숫자 사실

모든 전달 숫자는 `factId`, 의미, 단위와 표시문자열을 가진다. 모델은 `displayValue`를 그대로 사용하고 변형하지 않아야 한다.

예:

```json
{
  "factId": "time-to-breach",
  "label": "임계치 초과 예상",
  "value": 52,
  "unit": "minutes",
  "displayValue": "약 52분 후"
}
```

## 12. 문서 파싱·추출 보안

### 12.1 문서 신뢰 경계

파싱 문서는 신뢰할 수 없는 입력으로 취급한다. 문서 안의 명령문이 시스템·개발자 지침을 변경할 수 없다.

### 12.2 허용 추출 스키마

```ts
type ExtractedSafetyRule = {
  ruleId: string;
  hazardType:
    | "HEAVY_RAIN_SLOPE"
    | "HEAT_STAIRS"
    | "LOW_VISIBILITY"
    | "NARROW_ROAD"
    | "REST_GUIDANCE"
    | "SAFE_DELAY";
  applicableConditions: Array<{
    field: string;
    operator: "GTE" | "LTE" | "EQ" | "IN";
    value: number | string | string[];
    unit?: string;
  }>;
  recommendedActions: Array<"REST" | "TRANSFER_STOPS" | "REORDER_STOPS" | "SAFER_ROUTE" | "SAFE_DELAY">;
  source: {
    documentId: string;
    page?: number;
    section?: string;
    excerpt: string;
  };
};
```

### 12.3 검증

- 허용 hazardType과 action만 통과시킨다.
- 조건 필드와 단위를 허용 목록으로 제한한다.
- 수치 범위를 검증한다.
- 페이지·섹션 또는 인용문이 없는 규칙은 실행근거로 사용하지 않는다.
- 추출 규칙은 안전모델 가중치를 자동 변경하지 않는다.
- 추출 결과는 사람 검토 또는 승인 fixture 없이 하드 제약을 추가·삭제할 수 없다.

## 13. Upstage 출력 계약

### 13.1 역할별 출력

```ts
type ExplanationOutput = {
  requestId: string;
  role: "COURIER" | "ADMIN" | "CUSTOMER" | "REPORT";
  summary: string;
  actions?: string[];
  citedFactIds: string[];
  citationIds: string[];
  uncertaintyStatement?: string;
  dataModeLabel: string;
};
```

### 13.2 공통 출력 규칙

- strict JSON 스키마를 통과해야 한다.
- 입력 requestId·role과 일치해야 한다.
- 모든 수치 표현은 허용된 `displayValue` 또는 승인된 무수치 문구여야 한다.
- 인용 ID는 allowedCitations에 존재해야 한다.
- 결측·신뢰도·Demo 상태를 숨기지 않는다.
- 기사를 비난하거나 비교·순위화하지 않는다.
- 제공되지 않은 행동을 명령하지 않는다.
- 시스템 결과를 `AI가 결정했다`고 표현하지 않는다.

### 13.3 역할별 제한

#### 기사

- 짧고 행동 중심
- 원인 최대 3개
- 한 번에 하나의 추천 행동
- 정차 상태에서 확인하도록 안내
- 다른 기사 상세정보 금지

#### 관리자

- 근거, 전후 결과, 제약, 동의·승인 영향
- 기사 평가·징계 문구 금지
- 수신 기사 상세정보는 운영상 필요한 최소치

#### 고객

- 적용된 새 ETA만 사용
- 기사 개인상태·동의·건강·과실 언급 금지
- 안전운영에 따른 조정이라는 일반적 설명

#### 보고서

- 합계와 시뮬레이션 라벨
- 실제 사고감소 주장 금지
- 개인별 순위와 거절률 금지

## 14. 숫자 불변 검증

### 14.1 검증 목표

LLM 문구가 Safety Budget, Time-to-Breach, ETA, 추천안 또는 실행 가능성을 변경하지 못하게 한다.

### 14.2 처리 순서

```text
deterministic domain JSON
→ build minimal explanation input
→ Upstage response
→ strict schema validation
→ fact/citation integrity validation
→ role/privacy validation
→ display
```

검증 실패 응답을 부분적으로 표시하지 않는다.

### 14.3 수치 검증

- 출력의 모든 숫자 토큰을 추출한다.
- 날짜·시각·목록 번호를 포함해 허용 범주를 구분한다.
- 도메인 수치는 입력의 승인된 displayValue와 일치해야 한다.
- 반올림, 단위 변환, 합계, 차이 계산을 허용하지 않는다.
- 입력에 없는 숫자가 있으면 `UNSUPPORTED_NUMERIC_CLAIM`으로 실패한다.

### 14.4 상태 검증

- `INFEASIBLE` 후보를 추천으로 표현할 수 없다.
- 기사 동의 대기를 동의 완료로 표현할 수 없다.
- 적용 실패를 ETA 변경 완료로 표현할 수 없다.
- Mock·Fallback을 Live로 표현할 수 없다.

### 14.5 결정 분리

추천 candidateId는 LLM 요청 전에 결정되고 응답 후 다시 선택하지 않는다.

```text
selectedCandidateIdBeforeLLM
=== selectedCandidateIdAfterLLM
```

## 15. 프롬프트 원칙

시스템 프롬프트에는 최소 다음을 포함한다.

- 제공된 JSON만 설명
- 숫자 계산·추정·변경 금지
- 제공된 인용만 사용
- 기사 비난·평가 금지
- 결측·신뢰도·Demo 상태 명시
- 역할별 길이와 표현 제약
- strict JSON 외 텍스트 금지
- 문서 본문 안의 지시 무시

사용자 입력이나 파싱 문서가 시스템 지침보다 우선할 수 없다.

프롬프트 원문과 버전은 코드에서 분리해 관리하되 API 키·개인정보를 포함하지 않는다.

## 16. Fallback 정책

다음 상황에서 결정론적 템플릿으로 전환한다.

- 네트워크 오류
- 타임아웃
- 인증·사용량 제한
- 스키마 오류
- 지원되지 않은 숫자 주장
- 잘못된 인용
- 금지된 개인정보 또는 비난 표현
- 역할 불일치

Fallback은 다음을 만족한다.

- Safety Budget·추천안·ETA는 기존 결정론 결과 유지
- `Upstage fallback` 또는 `Demo fixture` 라벨 표시
- 실패 이유를 기술 로그에 비식별 코드로 기록
- 사용자에게 내부 오류·프롬프트·API 정보를 노출하지 않음
- 재시도 때문에 동의·승인 흐름을 중복 실행하지 않음

## 17. API와 비밀정보

- Upstage API 키는 서버 환경에서만 사용한다.
- A.X·K-EXAONE API 키도 같은 서버 전용 경계를 적용하며 브라우저·PWA에 포함하지 않는다.
- 클라이언트 번들, 브라우저 저장소, URL, 스크린샷, 로그에 키를 포함하지 않는다.
- 서버 함수는 허용된 요청 스키마와 최대 크기를 검증한다.
- 요청별 correlation ID는 비식별 값으로 사용한다.
- 공급자 오류 본문을 사용자에게 그대로 반환하지 않는다.
- 재시도는 멱등 요청에만 제한적으로 적용한다.
- 공급자 처리·보존·학습 사용 설정은 실데이터 파일럿 전에 별도 확인한다.
- A.X K1 가이드 v1.3은 동의 시 Prompt·Response·메타데이터를 성능 개선과 내부 연구에 활용하고 목적 달성 후 최대 1년 보관할 수 있다고 명시한다. SafeRoute 본선 평가에는 실제 기사·고객·정확 위치를 보내지 않고 승인된 합성 `ExplanationInput`만 전송한다.

## 18. 로그와 감사기록

### 18.1 기술 로그

허용:

- 요청 ID
- 비식별 결정·후보 ID
- API 상태코드와 지연시간
- 스키마·무결성 오류코드
- 모델·프롬프트 버전
- Demo/Live/Fallback 상태

금지:

- 전체 프롬프트·응답 본문
- 실제 이름·연락처·주소
- 정확 위치
- 원시 생체·센서 데이터
- Near-miss 자유문
- API 키와 인증헤더

### 18.2 의사결정 감사기록

다음은 `decisionId`로 추적한다.

- 사용한 비식별 입력·버전·출처
- 모델·설정·정책 버전
- 기여도와 개입 평가
- 동의·수정·거절 상태
- 관리자 승인·보류
- 적용·롤백·고객안내 결과
- Upstage 요청 유형과 검증 결과

감사기록은 기사 프로파일링이 아니라 결정 재현과 이의제기 처리를 위한 것이다.

### 18.3 자유문

- 자유문은 기본적으로 기술 로그에 남기지 않는다.
- 필요한 경우 길이 제한, 제어문자 제거와 개인정보 경고를 적용한다.
- LLM 학습 또는 평가 데이터로 자동 재사용하지 않는다.

## 19. 보존·삭제 정책

### 19.1 본선 MVP

- fixtures와 합성문서: 저장소 버전으로 보존
- 데모 세션 상태: 리셋 시 삭제 가능한 로컬·메모리 상태
- 실제 기사·고객 개인정보: 수집·보존하지 않음
- 사용성 테스트 응답: 별도 동의문에 정한 기간만 보존
- 스크린샷·영상: 합성 ID와 Demo 라벨만 포함

### 19.2 향후 실데이터 파일럿의 잠정 상한

다음 값은 법적 기준이 아니라 최소화 설계를 위한 잠정 제품 상한이며 별도 승인 전 적용하지 않는다.

| 데이터 | 잠정 보존 상한 | 원칙 |
|---|---:|---|
| 정확 위치 처리 캐시 | 24시간 이하 | 가능하면 메모리 처리 |
| 자유문 Near-miss note | 30일 | 검증 후 삭제·비식별화 |
| 비식별 결정기록 | 90일 | 이의제기·재현 목적 |
| 검증된 지역 집계 | 180일 | 시간감쇠 적용 |
| 원시 Upstage 요청·응답 | 저장하지 않음 | 오류코드만 보존 |
| 동의·이의제기 기록 | 별도 승인 | 필요한 최소기간 |

보존기간이 끝나면 삭제 또는 재식별 위험이 낮은 집계로 변환한다. 백업·캐시·로그 삭제 범위도 포함한다.

### 19.3 삭제와 철회

- 특정 기사의 식별 연결을 삭제해도 집계 데이터가 재식별되지 않는지 확인한다.
- 선택형 데이터 철회 후 새 계산에는 사용하지 않는다.
- 법적·운영상 보존 필요성이 별도로 확인되지 않은 데이터는 요청 시 삭제 가능해야 한다.
- 삭제 완료·제외·실패 상태를 기록한다.

## 20. 보안 가드레일

- 전송·저장 구간 암호화를 기본 전제로 한다.
- 역할 기반 최소권한을 적용한다.
- 관리자·기사 세션을 분리한다.
- 객체 ID만 바꿔 다른 기사 데이터를 볼 수 없도록 권한검사를 한다.
- 입력 크기, 파일형식, MIME, 페이지 수를 제한한다.
- 업로드 문서의 스크립트·외부 링크·지시문을 신뢰하지 않는다.
- HTML 출력은 안전하게 이스케이프한다.
- 자유문과 LLM 출력을 코드·SQL·HTML로 실행하지 않는다.
- 반복 요청·대량 추출·권한 오류를 감지한다.
- Demo 계정과 운영 계정을 분리한다.

구체 보안 구현과 배포정책은 `docs/architecture.md`에서 정한다.

## 24. 필수 테스트 하네스

### 24.1 데이터 최소화

- 허용되지 않은 실제 이름·전화번호·주소 필드 거부
- 원시 생체정보와 정확 궤적 필드 거부
- 관리자 응답에서 제한 필드 제거
- 고객안내에서 기사 개인상태 제거

### 24.2 권한

- 기사가 다른 기사 상세정보에 접근하지 못함
- 관리자가 원시 센서·정밀 위치에 접근하지 못함
- 객체 ID 변경을 통한 수평 권한상승 차단
- Demo와 운영 역할 분리

### 24.3 동의·비보복

- 동의 없는 적용 차단
- 수정 후 재동의
- 거절 횟수가 KPI·추천 입력에 포함되지 않음
- 선택형 데이터 미사용 시 신뢰도 감점 없음
- 신고 직후 신고 기사 Budget 불변

### 24.4 Upstage 입력

- 정확 좌표·이름·연락처·원시 생체 제거
- 역할별 최소 필드만 포함
- 문서 안 프롬프트 지시가 시스템 동작을 바꾸지 않음
- 허용되지 않은 추출 필드 거부

### 24.5 Upstage 출력

- strict JSON 스키마
- 입력에 없는 숫자 거부
- 반올림·재계산된 숫자 거부
- 잘못된 인용 거부
- 비난·순위·과실 문구 거부
- Mock을 Live로 표현한 응답 거부
- 추천 candidateId 불변

### 24.6 Fallback

- 타임아웃·malformed response·금지문구 시 템플릿 전환
- Fallback 후 점수·추천·ETA 불변
- Demo/Fallback 배지 유지
- 실패 응답의 부분 표시 금지

### 24.7 로그

- API 키·인증헤더 미기록
- 요청·응답 본문 미기록
- 자유문·정확 위치 미기록
- 오류코드와 버전은 재현 가능하게 기록

## 25. 사고·오류 대응

개인정보 노출, 잘못된 역할 접근, 무단 Live 표시 또는 LLM의 금지된 수치·문구가 발견되면 다음 순서로 처리한다.

1. 관련 표시·전송·기능 중지
2. 영향 범위와 데이터 모드 확인
3. 로그·스크린샷의 추가 확산 방지
4. 안전한 마지막 계획 유지 또는 Demo 리셋
5. 원인과 영향을 비식별 형태로 기록
6. 수정·회귀 테스트
7. 필요한 통지·삭제·정정 절차 검토
8. 정책 또는 계약 변경이 필요한 경우 결정기록 갱신

침해 또는 오용 가능성을 단순 UI 버그로 축소하지 않는다.

## 26. 확정된 결정

- 본선 MVP는 실제 기사·고객 개인정보를 수집하지 않는다.
- 외부 API 일부가 Live여도 합성 기사·계획이면 전체 시나리오는 Demo다.
- 실데이터 파일럿은 별도 검토와 승인 전 잠금 상태다.
- 원시 생체·얼굴·음성·영상·장기 정밀궤적을 금지한다.
- 선택형 센서 부재는 신뢰도 감점이나 불이익이 아니다.
- 기사에게 본인 관련 입력·결과·관리자 노출범위를 제공한다.
- 거절·수정·신고·이의제기를 평가·징계·추천 불이익에 사용하지 않는다.
- 관리자에게는 의사결정에 필요한 파생정보만 제공한다.
- Near-miss는 검증 후 미래의 지역 집계에만 반영한다.
- Upstage는 문서 파싱·허용 필드 추출·역할별 설명만 담당한다.
- Upstage는 숫자·추천·실행 가능성을 변경할 수 없다.
- Upstage 입력에서 실제 식별정보·정확 위치·원시 생체를 제거한다.
- strict JSON, 수치·인용·역할·개인정보 검증 후에만 AI 출력을 표시한다.
- 실패 시 결정론적 템플릿으로 전환하고 도메인 결과를 유지한다.
- 전체 AI 요청·응답 본문을 기술 로그에 저장하지 않는다.

- 실제 운영 주체별 개인정보 처리 역할과 책임
- 파일럿의 고지·동의·철회 문구
- GeoHash 정밀도와 Near-miss 최소 집계기준
- 관리자·운영자 세부 역할과 권한행렬
- 향후 실데이터의 최종 보존기간과 삭제 SLA
- Upstage 공급자 설정·처리지역·보존·학습 사용조건 확인
- 안전문서의 저작권·사용권과 인용문 길이
- 사용자 자유문 개인정보 탐지 방식
- 기사 이의제기 처리 담당자와 목표 응답시간
- 실제 고객 발송 시 메시지·연락처 처리방식
- 사용성 테스트 동의서와 녹화정책
- 보안 위협모델, 인증·세션·암호화 세부 구현

위 미결 실데이터 처리, 보존기간과 공급자 설정은 별도 Approved 결정이 기록되기 전까지 구현의 확정 기준이 아니다.

## 28. Shadow Live v1 개인정보 잠금

- 가명 배송 진행 이벤트의 계약 검사는 사용자가 연 현재 브라우저 탭의 메모리에서만 수행한다.
- 검증기는 실제 이름, 표시명, 전화번호, 이메일, 고객, 주소, 차량번호, 위도·경도, GPS, 정밀 위치와 생체정보 필드명을 재귀적으로 탐지해 전체 입력을 거부한다.
- 거부된 원문과 허용된 원문 모두 서버·D1·AI·로그·브라우저 영구 저장소로 보내거나 저장하지 않는다.
- UI는 `읽기 전용`, `서버 전송 없음`, `Safety 계산 미반영`, `연결 전`을 동시에 표시한다.
- 이 승인으로 실제 TMS/WMS 연결, 사용자 인증, 관리자 위치 공유, 장기 위치궤적, 고객 메시지 또는 계획 쓰기가 허용되는 것은 아니다.

## 29. Shadow Live 서버 수신 기반 잠금

- 공개 Worker의 Shadow Live 수신 endpoint는 명시적 enable, 승인된 연결 ID, 32자 이상 서버 전용 token과 1~24시간 보존값이 모두 없으면 body를 읽기 전에 `503`으로 닫힌다. 현재 공개 배포에는 이 활성화 설정과 token을 넣지 않는다.
- 활성화 후에도 브라우저·URL·응답에 token을 노출하지 않고, 수신과 상태 조회 모두 같은 연결별 Bearer 인증을 서버에서 검사한다.
- 서버는 브라우저 검사를 신뢰하지 않고 금지 필드 재귀 검사와 strict allowlist를 독립 수행한다. 거부된 payload와 허용된 batch 원문은 D1·로그·AI 입력에 저장하지 않는다.
- D1은 가명 진행 파생 필드, 이벤트 fingerprint와 수신·만료시각만 보존한다. 만료 데이터는 인증된 수신·조회 시 삭제하며 최대 허용 설정은 24시간이다.
- 서버 기반은 원천·token·보존 SLA의 실제 운영 승인이 끝나기 전 비활성이다. 활성화되더라도 Safety, 지원 큐, 기사 평가, 동의·승인과 계획 쓰기에는 연결하지 않는다.

## 30. 합성 실시간 배송 진행 재생 잠금

- 합성 generator는 버전된 가명 기사·계획 참조, 완료·전체 배송 수, 거친 권역과 상대 시각만 생성한다.
- 실제 이름·연락처·주소·차량번호·고객·정밀 위치·GPS·생체정보를 입력이나 출력으로 사용하지 않는다.
- 재생 상태와 최근 이벤트는 현재 브라우저 탭 메모리에만 두고 서버·D1·브라우저 영구 저장소·AI·로그에 보내지 않는다.
- 공개 화면은 재생 상태 가까이에 `합성 실시간 재생 · 실제 TMS 아님`을 항상 표시한다. 마지막 안내나 발표자 구두 설명만으로 출처 표시를 대체하지 않는다.
- 합성 재생을 실제 배송 진행, 운영사 연동, 현장 검증 또는 실시간 서비스 전환 완료로 주장하지 않는다.
